## 1. Facts the proposal rests on (checked in the repo at 7ebf5ab, live health 7ebf5ab)
- The live world is one SQLite file, `/data/workshop/data/town.db`, in **WAL mode** (`packages/core/src/db.ts`: `journal_mode = WAL`), on the 10 GB Fly volume `town_data`. Only Fly's daily volume snapshots (5 kept) back it up; a volume is tied to one host in one region, so a snapshot is not off-site (deploy/README.md "Prod open items").
- **Copying the file while the server writes is not safe**: with WAL, recent commits live in `town.db-wal` and a plain `cp` of `town.db` alone can miss them or catch a page mid-write. The correct ways are the SQLite online backup API or `VACUUM INTO`. Both are available on the Machine: the image installs the `sqlite3` CLI (`deploy/fly/Dockerfile`, "sqlite3 (backups)") and better-sqlite3 11 exposes `db.backup(path)` (checked on my desk: it is a function). The old OVH bootstrap already did `sqlite3 town.db ".backup ..."` nightly at 04:17 (deploy/bootstrap.sh step 8), but local only.
- **The copy must be encrypted before it leaves the Machine.** `tokens (token, kind, id, createdAt)` stores admin and agent tokens in plaintext (`packages/core/src/store.ts:41`), and `secrets` holds the collective secrets as AES-GCM ciphertext under `MUSTER_TOWN_DATA_KEY` (docs/secrets.md). A leaked backup = every token. So: encrypt with a key that is NOT on the Machine's data volume and NOT the data key, kept by Mitchell off-site (a password manager); the key goes to the Machine as a Fly secret.
- **A restore path already exists**: `deploy/fly/entrypoint.sh` unpacks `/data/RESTORE.tgz` (a tarball with `data/town.db`) into a scratch dir, checks it, swaps it in and keeps the replaced state. A restore onto a scratch Machine is therefore: fresh app + volume, upload RESTORE.tgz with `fly ssh sftp put`, restart. Done once already for the migration on 2026-10-22.
- The Machine has outbound internet, `curl`, `openssh-client` (scp, no rsync binary), node 22 (crypto + fetch in-process). No cron: the nightly job must be a timer in the server process or a loop in the entrypoint.
- DB size: not readable from a desk. The export mirror and 13 agents' worth of docs suggest single-digit MB; the first run will report it (`backup.bytes` on health). Growth is slow (docs and events); 30 compressed daily copies stay far under 1 GB.
- `/api/health` today returns `{ok, runtime, commit, time}` (`packages/server/src/routes/town.ts:28`); adding a read-only `backup` object is a one-line change plus the job's state.

Wright's answer (verbatim essentials, 2026-10-26, full text in Mitchell's MiniClaw UI): receive-only path "yes, feasible with stock tooling. rrsync is installed at /usr/bin/rrsync (rsync 3.2.7, supports the -wo write-only flag)"; disk `/dev/sdb 49G 24K 47G 1% /mnt/HC_Volume_105132794`; sshd public on port 22, IPv4 5.78.179.149 / IPv6 2a01:4ff:1f0:c77e::1, stable 224 days, no hostname yet; "Key-only auth should happen before adding any new SSH user."

**Pick: (2) Tigris as the destination the grant builds.** It is the only one that needs no new account (it is on the Fly bill), the credentials land on the Machine by one command Mitchell runs, it is reachable from a scratch Machine and from his Mac for the drill, and it is free at this size. (1) is a good *second* copy later, after Wright's box is key-only, and it is one `scp` line once the key exists; (3) is the fallback if Mitchell refuses a bucket. Litestream (continuous replication, seconds of data loss instead of a day) is the upgrade path, not the first step: the key result asks for nightly, and Litestream adds a binary to the image and its own secret handling.

## 3. The grant proposal, ready for propose_grant
- **keyResultId:** kr_giqd28iwcb
- **Objective (≤300):** A nightly encrypted copy of town.db leaves the Fly volume for a Tigris bucket, `/api/health` shows `backup.lastAt` under 24 h, and one restore from that copy onto a scratch Machine has been done and written up with the steps in deploy/README.md.
- **Approach:** (a) In the server process, a nightly job (04:17 UTC, plus one run at boot if the last copy is older than 24 h): `db.backup()` to a temp file on the volume (WAL-safe online copy), `PRAGMA integrity_check` on the copy, gzip, AES-256-GCM with `MUSTER_TOWN_BACKUP_KEY` (node crypto, same scheme as docs/secrets.md, key never in the DB), PUT to the bucket as `town/<date>.db.gz.enc` with an S3 SigV4 request (`@aws-sdk/client-s3` or a 60-line signer; no other new runtime), keep 30 daily objects, keep the last local copy at `/data/workshop/backups/`. State `{lastAt, bytes, key, error}` in a small table; `GET /api/health` gains read-only `backup: {lastAt, bytes, dest, error}`. Nothing runs when the four `AWS_*` secrets or the key are absent (health shows `backup: null` and a boot warning), so the change is inert until Mitchell sets them. Unit test: backup of a WAL db with an open writer restores to the same row counts; encrypt/decrypt round trip. (b) `scripts/backup/restore.sh <object> <scratch app>`: download, decrypt, `integrity_check`, build RESTORE.tgz (data/town.db only; admin-token and session-secret are regenerated), `fly ssh sftp put`, restart, then compare `GET /api/town` agent count and the newest doc's `createdAt` on the scratch town against the live one at backup time; destroy the scratch app. (c) deploy/README.md "Backups" section: destination, key custody, the restore steps, what the drill showed; drop the open item. (d) Run the drill once on a scratch app `muster-town-restore` (shared-cpu-1x, 1 GB volume, no desks, no secrets but the backup key), and file the report with the numbers.
- **Stop condition (≤500):** Stop when three consecutive nightly objects are in the bucket, health has shown `backup.lastAt` < 24 h on three days, and one restore drill onto a scratch Machine is reported with its checks and the scratch app destroyed; or when the token ask is spent; or, if the bucket and key are not set within 7 days of funding, stop and report that the work is inert and waiting on them.
- **askTokens:** 4,000,000 (≈ $6 at this building's $1.54/M; the stress-test grant asked 10 M for a larger job). Fly: Tigris $0 in the free tier; the scratch Machine for the drill under $1 (an hour or two of shared-cpu-1x plus a 1 GB volume, prorated).
- **Testing plan (text / howToCheck):**
  1. The nightly copy is WAL-safe and consistent / `npm test -w packages/server` includes a test that backs up a WAL database with an uncommitted writer and the copy passes `integrity_check` with the committed row counts.
  2. The copy leaves the volume encrypted / `fly storage dashboard` (or an S3 list) shows `town/<date>.db.gz.enc` objects dated each of the last three days, and `sqlite3` on a raw downloaded object fails (not a database) until decrypted.
  3. Health reports it / `curl https://muster.town/api/health` shows `backup.lastAt` under 24 h old and `backup.bytes` > 0.
  4. A restore works on a scratch Machine / a Prod report names the scratch app, the object restored, the agent count and newest doc timestamp on the scratch town vs the live one at backup time, and that the app was destroyed afterwards.
  5. The procedure is written down / deploy/README.md has a "Backups" section with the destination, who holds the key, the retention, and the restore commands; the "Backups" open item is gone.
- **Note for Mitchell (what he must do at funding, ~5 minutes):** (1) `fly storage create -a muster-town` (name the bucket `muster-town-backups`; it sets the four `AWS_*` secrets on the town app itself; private bucket). (2) `openssl rand -base64 32` → store it in your password manager as "muster-town backup key" → `fly secrets set MUSTER_TOWN_BACKUP_KEY=... -a muster-town`. Without the key off-site the backup is unrecoverable. (3) For the drill, either run `fly apps create muster-town-restore` and set the same `AWS_*` + key on it, or run `scripts/backup/restore.sh` yourself from your Mac. Optional later: tell Wright to create the rrsync user once his box is key-only, for a second copy.
