- **Mitchell:** why are we using a visitor to deploy? that seems weird

Redeploy checks the caller for the town.redeploy permission (routes/town.ts:654), so CI needs a token with that permission, and the only non-human thing that can hold one is an agent, hence a visitor named CI with the deployer role. It is a workaround, and it already bit us once: the ghost sweep saw a visitor that never showed presence and retired it. That hole is patched (app.ts:166-171 now stamps presence on every authenticated agent request). The alternative is you using your own user token in the secret, which makes every deploy act as you. - **Mitchell:** i'm still a little confused on the basics here. basically we have an API endpoint that pulls main and restarts the server, right? can't we just have a deploy token that you need to hit the endpoint, and then set that as a secret in github actions?
- **Secretary:** Yes, and that is exactly what we have. POST /api/admin/redeploy pulls the prod branch, rebuilds and restarts (routes/town.ts:652-658). CI calls it with a bearer token from the GitHub secret MUSTER_TOWN_DEPLOY_TOKEN. The one wrinkle is what a token is: every bearer token in this server belongs to somebody, a user or an agent (context.ts:90-99), and the endpoint checks that somebody for town.redeploy. There is no "bare" deploy token checked against an env var. So the token in the secret has to be owned by an identity, and we made that identity an agent named CI with only the deployer role. That is all the "visitor" is: the owner of the token. The thing to do now is unchanged: mint a token for a CI agent and put it in the secret. If you would rather have a bare env-var deploy token with no identity behind it, that is a small code change and I can queue it.
- **Mitchell:** is there any benefit to the deploy token having an identity, vs just being bare?
- **Secretary:** Some, but small. What an identity buys: (1) the record says who pressed it, "Redeploy requested by CI" in the events (runtime/redeploy.ts:281), and the drain logic uses that name to wait for the requester's own session (redeploy.ts:377); (2) revoke it like any other token, in the town, without touching GitHub; (3) permissions are roles, so "deployer and nothing else" is one role check, same gate as everyone (town.ts:654). What it costs: it is a fake resident, so every rule about residents applies to it, which is how the ghost sweep ate it, and it confuses people, as it just did you. A bare token in an env var gives up (1) and (2) for less to go wrong: the event would say "CI" by convention, and rotating it means editing two secrets. My view: the identity is not worth the lifecycle risk for a deploy hook. Both are fine today because the sweep hole is patched. I would mint the visitor token now so deploys work tonight, and separately queue a small change to accept a bare MUSTER_TOWN_DEPLOY_TOKEN env var on the redeploy route. Want me to queue that?
- **Mitchell:** ok another question while i'm groking this. why is the redeploy a push in the first place? couldn't the server pull the CI status for new commits and just redeploy itself?
- **Secretary:** It could, and nothing in the code stops it. Today the runtime has no watcher: redeploy.ts only runs when someone POSTs the route, and the "poll" in there is the drain loop, not a git check. The push shape is historical: the redeploy button came first for humans and agents, and CI was bolted on as one more caller. A pull would be simple because CI already does the hard part: it promotes main to the prod branch only when green, and redeploy already pulls prod. So the server would just fetch origin/prod every minute or so and, when it is ahead of what is running, start the same redeploy with requestedBy "prod branch". No GitHub token, no CI identity, no secret to rotate, no 401 ever again. Cost: up to a minute of latency, and the server watching itself instead of being told, which is fine for a box that already pulls its own code. I think it is the better design. If you want it, I will queue it as directed work from this 1:1 for Prod, who owns the deploy path, and you can skip minting the token if you are willing to press redeploy by hand until it ships.
